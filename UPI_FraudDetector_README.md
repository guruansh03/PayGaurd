# UPI Fraud Detection System

Unsupervised anomaly detection on synthetic UPI transaction data.
293k transactions · 6 fraud patterns · 3 ML models · Live Streamlit app.

---

## Why Synthetic Data

No public labeled UPI fraud dataset exists.
Synthetic data generated using documented fraud patterns from NPCI incident reports
and published fintech ML research. Standard practice in production fintech ML.

## Dataset — What We Generate

~293,000 UPI transactions across 2024. 19 domain-specific features.

### Features

| Feature | Type | Why It Matters |
|---|---|---|
| `amount` | continuous | Fraud skews high |
| `amount_log` | continuous | Log-normalised for ML |
| `amount_vs_sender_avg` | continuous | Sudden spike = red flag |
| `is_round_amount` | binary | ₹10k/₹50k/₹1L = known fraud signal |
| `txn_hour` | int | Late night = higher risk |
| `txn_day` | int | Weekday pattern |
| `is_weekend` | binary | Fraud spikes on weekends |
| `is_night` | binary | 11pm–4am flag |
| `velocity_1h` | int | Txns by same sender in last 1h |
| `velocity_24h` | int | Txns by same sender in last 24h |
| `is_new_device` | binary | Unknown device fingerprint |
| `cross_bank` | binary | Sender/receiver on different banks |
| `cross_state` | binary | Sender/receiver in different states |
| `upi_app_enc` | encoded | GPay / PhonePe / Paytm / BHIM etc. |
| `merchant_cat_enc` | encoded | P2P / food / fuel / utilities etc. |
| `sender_bank_enc` | encoded | SBI / HDFC / ICICI etc. |
| `receiver_bank_enc` | encoded | — |
| `sender_state_enc` | encoded | 15 Indian states |
| `receiver_state_enc` | encoded | — |

### 6 Fraud Patterns Injected

| Pattern | Signal | Count |
|---|---|---|
| Late-night high-value P2P | `is_night=1` + `amount > 20k` | ~500 |
| Rapid velocity | `velocity_1h > 5` | ~500 |
| New device + high amount | `is_new_device=1` + `amount > 30k` | ~500 |
| Cross-state impossible travel | `cross_state=1` + new device | ~500 |
| Round amount transfers | `is_round_amount=1` | ~500 |
| Dormant account spike | `amount_vs_sender_avg >> 1` | ~500 |

`fraud` column exists but **never used during training** — unsupervised only.
Used only for post-hoc evaluation (Precision, Recall, ROC-AUC).

## Screenshot OCR Setup

The live scorer can auto-fill fields from a UPI screenshot, but that feature needs the Tesseract binary in addition to `pytesseract`.

For Windows local runs:

1. Install Tesseract OCR.
2. Add `tesseract.exe` to your `PATH`, or set the `TESSERACT_CMD` environment variable to the full executable path.
3. Re-run the app and upload the screenshot again.

For Streamlit Cloud, `packages.txt` already installs `tesseract-ocr`.

## Models

| Model | How it detects UPI fraud |
|---|---|
| **Isolation Forest** | Randomly partitions feature space. Fraud (high velocity, new device, late night) isolates in fewer splits → high anomaly score. |
| **Autoencoder** | Trained only on normal transactions. Fraud patterns (unseen combinations) have high reconstruction error. |
| **DBSCAN** | Density clustering. Fraud transactions don't cluster with normal ones → labelled as noise. |

## Professor Q&A — Key Points

**Why synthetic data?**
No public labeled UPI fraud dataset exists. Synthetic generation with domain-realistic fraud patterns is standard in fintech ML research. Our fraud patterns mirror documented NPCI incident types.

**Why unsupervised?**
In real deployments, fraud labels are delayed (chargebacks take days), incomplete, and adversarially noisy. Unsupervised models learn normal behavior — anything outside that boundary gets flagged.

**What makes this UPI-specific?**
Velocity features, device fingerprinting, cross-state signals, round-amount detection, and UPI app/bank encoding are all domain-driven. These are the exact signals used in production UPI fraud systems.
